## 优先发现

共列 8 个改进项：P0 0、P1 风险 1、P2 6、P3 1。P1 的异常保护缺口已确认，触发效果尚未故障复现；性能和大字体候选也不能称为已经发生卡顿或裁切。

### [P1] 下载恢复与调度缺少最外层异常隔离

类别：可靠性。
位置：[Downloads.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/Downloads.kt:39)、[DownloadStore.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/DownloadStore.kt:63)。

已确认：初始化直接执行 store.recover() 后才置 ready=true。恢复 DELETING 调用 removeFiles()，删除失败可抛出异常。start() 先置 processing=true，循环取任务和写入 RUNNING 的操作在 transfer() 异常保护之外；transfer 的 catch/finally 自身还会访问 SQLite。

影响：存储读取、写入或删除异常时，可能中断恢复/调度，并缺少保证状态复位的路径。不能将其写成已复现的磁盘占满故障。

建议：每条恢复记录隔离异常；调度循环最外层保证状态清理；低空间先暂停并给出可恢复提示；补存储故障与损坏记录测试。
对应命令：$impeccable harden（界面错误状态），调度与持久化修复另按代码工作流进行。

### [P2] 在线与离线观看记录彼此分离

类别：任务体验一致性，新增能力。
位置：[PlaybackService.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/PlaybackService.kt:152)、[DownloadStore.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/DownloadStore.kt:54)、[MediaDatabase.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/MediaDatabase.kt:137)、[VideoDetailActivity.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/VideoDetailActivity.kt:180)。

已确认：download: 分支只写下载库 position 并直接 return；普通视频写 playback。最近播放只 JOIN playback。下载完成后详情优先采用下载记录中的位置。

影响：离线观看不会更新视频库最近播放；同一文件在线/离线切换时采用另一套位置。这是当前设计的行为边界，属于体验改进，不是已经证实的数据损坏。

建议：按账号、消息和 document 身份统一最近观看时间及续播位置；让下载完成后的续播衔接已有观看位置。设计时需兼顾退出账号后独立离线观看。
对应命令：$impeccable shape。

### [P2] 下载进度刷新带着全部历史记录一起读取和更新

类别：性能。
位置：[Downloads.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/Downloads.kt:40)、[DownloadStore.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/DownloadStore.kt:32)、[DownloadsActivity.kt](/Users/long/Documents/CodexProjects/tgproxy/android/app/src/main/java/dev/tgproxy/mobile/DownloadsActivity.kt:56)。

已确认：每次进度写入后 changed() 全量查询并解析所有下载记录；传输约每 500ms 或每个 1MiB 段结束报告进度。页面每 700ms 刷新/遍历记录，采用 ScrollView + LinearLayout，完成历史没有分页。行 ID 未变时会保留原行，并非每次进度都重建整个页面。

影响候选：完成记录越来越多时，数据库读取、对象分配、主线程测量和更新成本增长；实际卡顿和功耗尚未测量。

建议：只更新当前任务快照，状态增删时再更新列表；完成记录分页；采用回收行和可见行增量刷新，保留紧凑文字布局。
对应命令：$impeccable optimize。

## 系统性模式与已有优点

- 下载库历史记录与实时进度耦合，扩展到大规模时成本随全部记录增长。
- 在线/离线数据边界清楚，后续统一体验时需要在媒体身份和账号归属上建立一致规则。
- 数据库查询多数已异步，少数同步频道读取值得沿用既有后台快照模式补齐。
- 小图标与小命中容器被同时压缩，应把视觉大小与点击范围分开。
- 逐页索引事务、独立历史/新增游标、校验不完整时保留索引、document/ETag 防混片、会话加密、账号检查、后台媒体所有权与暂停续传都值得保留。

## 新增能力候选（不作为现有缺陷计数）

1. 全部继续 / 批量重试：进程恢复会把排队和运行任务改为暂停；现有只有全部暂停、单项继续。按原账号过滤、一键恢复队列，比增加并发更先解决操作负担。
2. 弱网恢复：下载采用失败后手动重试；播放器有内核重连和 Media3 默认行为，但终止错误后 App 提示点击重试。可增加有限重试、等待网络恢复及更明确的错误分类。
3. 同频道选片、上一条/下一条、可选连续播放：当前 setMediaItem() 单媒体且隐藏上一条/下一条；采用文字选片面板，不需要改变视频库视觉方案。
4. 下载列表搜索/过滤及“已下载”标识：有助于查找离线资源，优先于增加展示模式。
5. 整批频道任务恢复为待继续：当前队列仅在内存，页游标持久化；可以保存批次、模式和待处理频道，让用户一键继续。
6. 旧消息变化发现：新增更新只追水位以上，资源校验仅查询已经索引的视频 ID。原非视频旧消息被编辑成视频的场景需回扫/更新事件能力；不应宣称现有校验能发现一切旧消息变更。
