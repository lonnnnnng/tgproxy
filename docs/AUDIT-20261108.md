# 审计记录（2026-11-08）

> 历史记录。当时使用的媒体服务器现已替换为 Emby，本文只保留与 tgproxy 自身相关的结论。

## 背景

用户已添加频道、扫描并重建媒体树，但媒体服务器网页端为空。排查确认：

- 媒体服务器当时关闭了实时监控，最后一次扫描早于媒体文件生成
- tgproxy 原来的重建操作没有通知媒体服务器刷新
- 宿主与媒体服务器读取的目录一致、权限可读，排除挂载问题

## 暴露出的 tgproxy 缺陷

媒体服务器开始扫描后，进一步暴露拉流尾块 bug：

- 最后一块请求长度向下取整到 4096 倍数，剩余不足 4096 时发出零长度请求
- 导致 MP4 尾部索引丢失；旧版本返回 206 和 Content-Length，但实际返回 0 字节
- `ffprobe` 报提前 EOF、STSZ/STCO 截断

该缺陷属于本项目实现，不能归因于 tdl。

## 修复与验证

| 项目 | 结果 |
|------|------|
| 控制台 | 扫描自动重建并通知媒体服务器；任务互斥；失败频道保留旧索引并显示错误 |
| 配置 | 数值/URL 校验，flag 覆盖文件配置，原子私有文件保存；通知请求不带密钥跟随重定向 |
| Range | 单区间、后缀 Range、`206`/`416`、4096 对齐尾块 |
| 服务器 | 实际重建确认 466 个文件，根 inode 保持不变，媒体服务器通知成功 |
| 探测 | 两个原失败视频在媒体服务器所在主机用 `ffprobe` 返回 0，识别 H.264/AAC、尺寸和时长 |
| 流验证 | 媒体服务器实际条目的流请求返回 206、`video/mp4` 和完整 1024 字节 |
